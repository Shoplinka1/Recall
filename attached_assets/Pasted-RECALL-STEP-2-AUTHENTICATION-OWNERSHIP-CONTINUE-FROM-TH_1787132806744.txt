2. AUTHENTICATION

Implement/repair:

POST /api/auth/signup
POST /api/auth/login
POST /api/auth/logout
GET /api/auth/me

Requirements:
- secure password hashing using Argon2 or bcrypt
- persistent sessions in PostgreSQL
- secure session cookies
- session expiry
- logout invalidates the session
- duplicate email protection
- useful safe error responses

Never store plaintext passwords.

Never expose passwords or session secrets.

==================================================
3. PROTECTED ROUTES

Authenticated users must be required for user-owned API operations.

At minimum protect existing routes involving:

- subjects
- materials
- concepts
- questions
- practice sessions
- attempts
- progress
- subscriptions/payments if currently exposed

Do not rely on frontend authentication.

The server must determine the authenticated user from the session.

==================================================
4. OWNERSHIP

Every user-owned database record must be checked server-side.

A user MUST NOT be able to access another user's:

- subjects
- materials
- material sections
- concepts
- questions
- practice sessions
- attempts
- progress/mastery
- weaknesses
- recommendations
- subscriptions
- payments

Never trust a userId supplied by the browser.

Use the authenticated session userId.

For routes using an ID:

GET /api/materials/:id

for example, verify that the record belongs to the authenticated user before returning it.

Do the same for update/delete/practice operations.

==================================================
5. CROSS-USER SECURITY TEST

Create tests proving:

User A creates a subject/material/practice session.

User B attempts to access those records.

User B MUST receive an appropriate unauthorized/not-found response.

Test at least:

- another user's subject
- another user's material
- another user's practice session
- another user's attempts/progress

Also test that an unauthenticated request cannot access protected data.
